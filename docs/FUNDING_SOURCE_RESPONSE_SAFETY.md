# Grants.gov response safety and scientific-data provenance

The EYLO Funding and Opportunity Radar pages use two official read-only
Grants.gov APIs:

- `POST https://api.grants.gov/v1/api/search2`: search for posted and
  forecasted funding listings.
- `POST https://api.grants.gov/v1/api/fetchOpportunity`: get a specific
  listing's detailed synopsis, categories and eligibility.

See the official documentation:
https://www.grants.gov/api/common/search2 and
https://www.grants.gov/api/common/fetchopportunity.

## Release-candidate safety controls

- The backend reads JSON through a **bounded stream**, not through
  unbounded `response.json()`. Maximum received body sizes are
  **2 MiB per search** and **1 MiB per detail**.
- A claimed `Content-Length` over the limit is rejected early, while
  a streamed response over the same limit is also stopped even if that
  header is absent or wrong. A non-JSON media type, empty body or
  malformed JSON are source errors, **never successful zero results**.
- Search responses with missing/invalid opportunity IDs are rejected as
  unusable instead of inventing or silently dropping search hits.
- If a detail request fails, the *official search listing* is still
  returned, but with `detail_status: unavailable`. The overall
  response includes `partial_results: true` and
  `detail_unavailable_count`. **Eligibility, description and amount
  are left blank**, not inferred from the title or generated by AI.
- Both funding interfaces show a visible warning for partial results,
  label results as official listings rather than fully verified records,
  and instruct the AI ranking prompt not to infer unavailable details.
- API responses carrying a researcher's private funding query use
  `Cache-Control: private, no-store`, including errors.

All regression tests use local mock streams and simulated official API
records. They do not certify the current Grants.gov availability or the
correctness of live funding deadlines, eligibility or awards. Before
launch, test a representative real sample, mismatched dates and
eligibility text against official linked notices. These source limits
may require adjustment based on measured real provider payload sizes,
but must never be disabled silently.

This patch does not enable Stripe billing, Supabase access, or scheduled
monitoring. It remains part of the **draft integrated PR #203**, not
production.
